# Paper plugin conventions

Baseline rules for any change to a Team-Sneakymouse Paper plugin, however small. For larger design questions, see [Paper plugin maintainability](./paper-plugin-maintainability.md).

- **Main thread:** do disk, database, Pocketbase and HTTP calls in async tasks; return to the main thread only to touch Bukkit state. No blocking calls in event handlers.
- **Reload:** when adding config fields, caches, tasks or listeners, clear and rebuild them in the reload path. Cancel old scheduled tasks before starting new ones.
- **Boss bars / MythicHUD:** reserve yellow boss bars for MythicHUD; other plugins must choose a non-yellow bar color (`BossBar.Color.YELLOW` / Bukkit `BarColor.YELLOW` must not be used for ordinary plugin bars). MythicHUD's resource pack makes the yellow boss bar background transparent regardless of its `boss-bar.color` setting, so yellow cannot provide the expected visible background. Apply this to defaults and configurable bar colors; explain the reserved color and use a non-yellow fallback or reject yellow explicitly. Do not work around it by overriding MythicHUD's pack assets. See [MythicHUD architecture](https://github.com/Team-Sneakymouse/craftengine-resources/blob/main/docs/architecture.md#mythichud).
- **Animated visuals:** prefer ModelEngine for anything that needs animation or would benefit from it; proactively suggest useful animation rather than defaulting to static visuals or bespoke display-entity rigs. Keep optional work within agreed scope. See [animation and blueprint ownership](./paper-items.md#animation-prefer-modelengine).
- **Block damage and temporary state:** any plugin that causes block damage or makes any temporary change to block state must route it through SneakyUtils' shared `AlteredBlockManager`, obtained via `SneakyUtils.getAlteredBlockManager()`. This includes non-destructive changes, even when the block material stays the same. Do not bypass shared tracking or introduce a separate restoration manager. See [block damage and restoration](./sneakyutils.md#block-damage-and-restoration).
- **Build protection:** SneakyPlots decides what a player may place, break or use where. A plugin whose players place, remove or use its own things in the world (canvases, furniture, machines) asks SneakyPlots rather than querying regions or plots itself. When the player acts, call `SneakyPlotsApi.attempt(player, action, thing, location)` with a key of your plugin (`<plugin>:<thing>`) and stop when it returns false; it shows the deny feedback itself. To ask ahead (a menu, a preview), call the silent `allows(...)`. Mark every entity of the thing a player can click with the PDC key `sneakyplots:thing` (a string holding that id), so SneakyPlots checks clicks and damage against the id and not the entity type. Items need no mark: a SneakyItems magic item is `sneakyitems:<name>`. The id is a stable id named in `rules.yml`, and only a grant for that id or `*` allows it, so report which rule entries a new thing needs. SneakyPlots' `README.md` ("For other plugins") documents the API.
- **Public hooks:** MagicSpells spell names, variables and dispatched console commands are an API used by MagicSpells-Data (branch `dev`) and other plugins. Search those callers before renaming or changing arguments.
- **Worn models:** a model worn on a player outside an equipment slot (backpack, shell, hat over a helmet) is a SneakyCosmetics back or head item, not a plugin-local riding `ItemDisplay` with its own pose/remount/visibility loop. See [SneakyCosmetics](./sneakycosmetics.md).
- **Display-only GUIs:** a menu that shows plugin-built icons (not a place players store items) must open a location-free virtual container and must be skipped by SneakyItems' magic-item updater/expiration. See [display-only GUI inventories](./sneakyutils.md#display-only-gui-inventories). Storage UIs that intentionally move real items (vaults, charadmin, bags) stay ordinary inventories.
- **Player-facing names:** show character names via SneakyUtils `PlayerUtil.getCharacterName(player)`, not Minecraft account names. The only exceptions are admin/moderation tools and command auto-completion, which may use Minecraft names. See [the shared getter contract](./sneakyutils.md#player-facing-character-names).
- **Stable ids:** don't rename `lom:` `item_model` ids or PDC keys; existing items and entities depend on them. Add a migration or keep the old key.
- **Item identity:** placeable/usable stacks share MagicSpells' `magicspells:magicitem` PDC name; look stays on `item_model`. See [custom look / identity](./paper-items.md#custom-look).
- **Effect recipients:** use SneakyUtils `PlayerUtil.canTarget(player)` for who may be hit, pulled, drained, randomly chosen, or counted in an AOE/prey pool. Default excludes Creative; Spectator is never eligible; keep self-ability gates, item-consume creative exemptions, and viewer `canSee` separate. Known product exceptions (Knives Knife Fairy visits; Haunted station wait/kit/call) and anti-patterns are in [target eligibility](./sneakyutils.md#player-eligibility-for-targeted-and-random-effects).
- **Reflection:** use compile-time imports and Gradle dependencies (`compileOnly` / soft `depend`) instead of `Class.forName`, `getMethod`/`getDeclaredMethod`, or MethodHandles for any type you can resolve at build time. Soft optional plugins that publish artifacts still use imports plus runtime enablement checks, not reflective lookup. Placeholder expansion goes through SneakyUtils `PlaceholderUtil` rather than local PAPI reflection or a local PAPI compile dependency solely for `setPlaceholders`. **NMS / CraftBukkit packet and entity internals may keep reflective lookup** — those surfaces are volatile across Minecraft versions and typed imports win little over the existing update burden. Outside NMS, reserve reflection for unpublished foreign APIs with no practical typed alternative. See [cross-plugin contracts](./paper-plugin-maintainability.md#cross-plugin-contracts) and [placeholders](./sneakyutils.md#placeholders).
- **Docs:** when commands, permissions or config keys change, update the relevant documentation in the same commit. Update AGENTS.md only when its instructions or context pointers change; keep shared conventions in this policy and implementation details beside the code or in task-specific documentation.
